## A. PROJECT IDENTITY

- **Project Name**: STHARA — 3D Cadastral Intelligence
- **Current Product Description**: Next-Generation 3D Spatial Cadastre, Volumetric Land Rights Modeling, and Prototype 3D-ULPIN Platform. Fuses 2D cadastral parcels, OpenStreetMap (OSM) vector layers, elevation models (DEM), architectural floor plans, and structural drawings into validated 3D polyhedral property models.
- **Current Product Purpose**: To eliminate vertical rights ambiguity, detect 3D spatial encroachments/overhangs, and assign deterministic, stratified 3D property identifiers to multi-storey units and subsurface structures.
- **Current Product Hierarchy**:
  ```text
  Dataset
  └── Building
      └── Floor
          └── Unit
              └── 3D Solid
  ```
- **Current Product Terminology**:
  - `Dataset`: Top-level spatial container (e.g. Pune testbed, Tagore Garden, or custom uploaded project).
  - `Building`: Physical 3D building shell extruded from 2D footprint polygon ($Z_{base} \dots Z_{roof}$).
  - `Floor`: Stratified horizontal slab derived from floor height slicing ($Z_{min} \dots Z_{max}$).
  - `Unit`: Stratified 3D property volume (apartment/office/shop) inside a floor.
  - `3D Solid`: Closed, watertight polyhedral mesh manifold conforming to Canonical 3D Geometry Contract v1.0.

- **STRICT TERMINOLOGY BOUNDARY**:
  > **Explicitly state**: The spatial identifier generated by this system is a **STHARA Spatial ID** (or Prototype 3D ULPIN).
  > It is **NOT**:
  > - An official government ULPIN (Bhu-Aadhaar)
  > - A government property ID
  > - An ownership ID or legal land title
  > - A legally binding cadastral registry deed

## B. PRODUCT VISION

*(Extracted from authoritative `PRD.md` and `ARCHITECTURE.md`)*

- **Problem**: Traditional 2D cadastral records project land boundaries onto planar surfaces, creating critical urban limitations:
  1. *Vertical Rights Ambiguity*: Inability to define stratified ownership rights above/below ground (apartments, basements, utility conduits, elevated transit).
  2. *Hidden Geometric Clashes*: 2D projections cannot model vertical cantilever overhangs, shared party-wall interfaces, or subterranean easement penetrations.
  3. *Inadequate Stratified Identification*: Traditional 2D land parcel numbers fail to uniquely identify individual 3D vertical units.
- **Solution**: Web-based geospatial platform that ingests 2D cadastral layers, building footprints, DEM elevation data, and architectural/structural drawings; normalizes CRS to metric UTM coordinates; extrudes watertight 3D polyhedral property volumes ($Z_{min}$ to $Z_{max}$); executes automated 3D spatial containment and clash detection; assigns deterministic **STHARA Spatial IDs**; and renders an interactive 2D GIS map alongside a 3D WebGL WebGL cadastre.
- **Target Users**:
  - Cadastral & Revenue Officers (evaluating 3D volumetric subdivisions).
  - Urban Local Bodies (ULBs) & Municipal Planners (detecting vertical overhangs & encroachment).
  - Surveyors & GIS Professionals (validating spatial data & GNSS control points).
  - Property Owners & Citizens (inspecting 3D unit bounds and volumetric rights).
- **Core Workflow**:
  1. Ingest project data (GeoJSON, OSM XML, or Architectural/Structural PDFs via Project Data Entry).
  2. Geo-reference & reproject coordinates to local projected metric grid (`EPSG:32643` UTM Zone 43N).
  3. Validate 2D footprints & derive floor/basement height intervals.
  4. Extrude closed 3D polyhedral manifolds for surface columns, building shells, floors, and units.
  5. Run 3D topological validation (containment, vertical overhang, volumetric overlap).
  6. Generate cryptographically verified **STHARA Spatial IDs** (Prototype 3D ULPINs).
  7. Render dual 2D map / 3D WebGL WebGL stage with interactive floor-explode slider and property inspector.
  8. (Optional) Request non-authoritative Gemini natural-language summary.
- **Major Capabilities**:
  - Deterministic 3D polyhedral extrusion (Watertight manifold, Euler characteristic $V - E + F = 2$).
  - Multi-source spatial data fusion & provenance lineage tracking.
  - Automated Drawing Intelligence (PDF upload, page rendering, sheet classification, region detection, footprint extraction, drawing-only fallback mode).
  - 3D spatial measurement tools (distance, area, volume).
  - Wavefront OBJ & 3D GeoJSON export.
- **Planned Architecture**: Microservices-capable decoupled Next.js + FastAPI architecture, designed for optional future PostGIS and cloud deployment while running zero-friction local fast-track spatial registry.
- **Current Implementation Boundary**: Real OSM footprints (Tagore Garden, Delhi) are treated as **unverified physical surface observations** (`is_cadastral=False`), keeping legal cadastre title separate from crowd-sourced physical observations.

### Dataset Isolation & `activeDatasetId` Flow
- `activeDatasetId` is the primary state variable identifying the isolated project scope (e.g., `ds_west_bengal_empty_osm_test`, `ds_tagore_garden_map_osm`, or `ds_pune_demo`).
- Passed via `x-dataset-id` HTTP request header or query parameter `dataset_id`.
- Backing services resolve dataset paths dynamically (e.g. `data/uploads/drawing_intelligence/<activeDatasetId>/`).
- Switching datasets clears active Three.js mesh instances and re-fetches parcel/building/floor/unit data exclusively within the target dataset's namespace.
